# NVIDIA VSR、功能切换与性能浮窗

## VSR 使用

在“视频 → RTX 设置”或串流中的 RTX 面板选择 NVIDIA VSR：关闭、低、中、高、极高。此实现处理 SDR；HDR 保留原有 NR 路径和普通缩放。运行于 Windows Vulkan 渲染器，要求兼容的 NVIDIA RTX 显卡与驱动。

运行库放在主程序目录下的 `runtimes/nvngx_vsr.dll`。本机 `release/ngx` 已准备；可分发 ZIP 保持不包含 NR、VSR 这两项用户提供的 DLL。

当前验证并锁定 NVIDIA RTX Video SDK 1.1 的 `nvngx_vsr.dll` 1.6.0.0：

```text
SHA256 c3d88eea5ff7a548edefa66414cf6e77464d0947277c904f324dd23abf58a1ed
```

优先从 [NVIDIA RTX Video SDK](https://developer.nvidia.com/rtx-video-sdk) 或 [NVIDIA NGC 的 SDK 文件](https://catalog.ngc.nvidia.com/orgs/nvidia/multimedia/models/dlpp/1.5/file-browser)取得运行库。此次官方端点连接失败，本机测试 DLL 取自 [dlss5-video-player v0.30.0 的完整程序包](https://github.com/2600th/dlss5-video-player/releases/tag/dlss5-video-player-v0.30.0)，提取后检查 NVIDIA Corporation 的有效 Authenticode 签名、版本及上述哈希，没有运行该程序包中的其他程序。DLL 受 NVIDIA 自身许可约束。

参考 [FzeNiX/chiaki-ng-enhanced](https://github.com/FzeNiX/chiaki-ng-enhanced) 提交 `9e878112dbc89d0edd326ee80a7f8cf55ee9185b` 的 `gui/src/rtxvsr.cpp`：使用 NGX feature 16、`Input1` / `Output`、`Rect.*` / `OutRect.*`、`VSR.QualityLevel` 参数。本项目将其接入现有 MSVC D3D12 增强进程；协议当前为 9，GUI 和增强进程必须同时更新。输入共享纹理保留原始可见区域分辨率，VSR 输出到窗口目标分辨率，随后执行 DLSS FG。

只接入 1.6.0.0 支持的四档超分模式。参考项目中的 Artifact Reduction / Streaming 扩展模式需要更新运行库，当前不提供这些未验证选项。

## 链路顺序与性能调整（协议 9）

默认顺序为 `解码 → VSR → NR → DLSS FG → 调色 → 呈现`：VSR 先在源分辨率画面上去压缩伪影并放大到窗口目标分辨率，NR 和插帧不再放大串流伪影。此顺序下 NR 分辨率百分比相对于 VSR 输出计算，例如 1080p 串流、1440p 窗口时 75% 即 1920×1080；NR 的差值按普通缩放叠回输出。启动串流前设置环境变量 `CHIAKI_ENHANCEMENT_CHAIN=nr-first` 可恢复旧顺序（NR 在源分辨率 → VSR），用于对比。VSR 运行库缺失或评估失败时，前置阶段改用普通缩放，NR/FG 继续工作。HDR 不受影响。

同时调整：

- 光流始终在源分辨率上计算，向量按比例换算到 NR 和插帧分辨率。不超过 1080p 时默认使用 NVOFA 中等质量档，更大时保持快速档；`CHIAKI_ENHANCEMENT_FLOW_QUALITY=fast|medium|slow` 可覆盖。耗时显示在浮窗的插帧分项里。
- 每帧的 GPU 阻塞等待由约 8 次减为 3 次：HDR 代理、场景切换缩略图和光流亮度合并为一次提交；缩略图使用常驻回读缓冲；光流参考帧改为交换而不是复制。
- 插帧输出校验只在增强进程启动后进行一次，场景切换只重置时域历史，不再触发全分辨率 CPU 回读。
- 生成帧按微秒级截止时间排帧，间隔取串流标称间隔并做平滑，不再使用取整毫秒。
- 关闭垂直同步且启用应用内 DLSS FG 时，交换链在显示表面支持的情况下使用 MAILBOX（不阻塞、不撕裂），否则保持 IMMEDIATE。该选择在创建交换链时生效，串流中途开关插帧不会切换。

以上调整尚未在 RTX 硬件上构建和实测：提交这些改动的机器没有 MSVC、NGX SDK 和 NVIDIA 驱动。合并前需重新构建 GUI 与增强进程并运行 `enhancement-model-test`、`--self-test` 和桥接测试。

## 运动向量精修与置信度回退

目标是减少插帧的“果冻”扭动，对 3x/4x 和 30 fps 源尤其重要。以下处理只在增强进程内部进行，协议版本不变：

- **全局运动模型**：每帧把光流网格读回 CPU（约 1500 个采样点），用确定性 RANSAC 加最小二乘拟合仿射相机运动（平移、缩放、旋转）。至少 35% 的采样点一致时才采用。与模型相差不到约 0.75 像素的向量直接替换为模型值，背景因此作为一个刚性面移动；差异更大的区域保留局部光流。实现见 `gui/enhancement/motion_model.h`，`enhancement-model-test` 覆盖拟合结果。
- **保边上采样**：光流网格先做 3×3 中值滤波，再以当前帧亮度为引导做联合双边上采样，运动边界跟随画面边缘，不再被双线性插值抹平。NR 和插帧使用同一套向量。
- **置信度回退**：按运动补偿后的前后帧亮度误差计算置信度（平均绝对误差低于 0.06 为可靠，高于 0.14 为不可靠）。DLSS FG 输出到私有纹理，再按置信度与最近的真实帧混合：不可靠区域重复真实帧，局部可能略有顿挫，但不扭曲。前半段相位取上一真实帧，后半段取当前真实帧。

开关：`CHIAKI_ENHANCEMENT_MOTION_REFINE=off` 恢复原始光流向量并停用全部三项；`CHIAKI_ENHANCEMENT_FG_FALLBACK=off` 只停用回退。日志中的 `[RTX][Motion]` 行报告是否启用、全局模型是否成立及内点比例。新增着色器编译失败时自动退回原路径。

限制：置信度以当前帧坐标计算，中间帧上的运动物体位置与掩码有小幅错位；阈值（吸附 0.75 像素、误差 0.06/0.14、亮度相似度 0.08）是未经画面对比的初值。着色器已用系统 D3D 编译器通过 cs_5_0 编译；C++ 部分与其余改动一样尚未构建和实测。

### 2026-11-13 录像对照后的默认值调整

四段真实 120 fps 录像、8,130 张配对生成帧的开关对照显示：向量精修对 DLSS FG 输出几乎没有影响（平均 PSNR 差约 0.00002 dB），置信度回退平均降低 0.253 dB，并在快速运动的画面边缘填入位置不匹配的真实帧像素。据此：

- 置信度回退改为默认关闭，`CHIAKI_ENHANCEMENT_FG_FALLBACK=on` 才启用。
- 向量精修在 DLSS FG 后端下默认关闭（`CHIAKI_ENHANCEMENT_MOTION_REFINE=on` 可强制开启）。
- 新增实验性后端 `CHIAKI_ENHANCEMENT_FG_BACKEND=flow`：不调用 DLSS FG，沿光流向量对前后真实帧做运动补偿插值；两侧取样不一致或一侧出画时，改用时间上更近或仍在画面内的运动补偿取样。该后端直接使用向量，精修默认开启。当前仍要求 DLSS FG 运行库存在。
- 新增诊断 `CHIAKI_ENHANCEMENT_FG_VECTORS=zero`：给 DLSS FG 全零向量。若输出与正常向量基本一致，说明 DLSS FG 主要依赖自身内部光流，改进输入向量无法改善其画质。
- `[RTX][Motion]` 日志在全局模型被拒时也报告 RANSAC 最佳一致数（`agreeing=最佳/采样`）以及缩放项，用于确认被拒原因。

上面“置信度回退”一节描述的是可选行为，不再是默认行为。自建后端和两项诊断尚未在 RTX 硬件上运行。

### 2026-11-14 六配置复测后的调整

同素材 8,130 张配对帧的结论：DLSS FG 对输入向量不敏感（零向量与正常向量平均相差 0.0026 dB）；自建后端在路杆等细长结构上明显好于 DLSS FG，静止画面高约 8 dB，但在慢速运动上输给线性混合（76% 的帧），在快速转向处撕裂成块状；全局模型的一致率中位数只有 16%。据此修改自建后端：

- 每个像素比较“沿向量运动”和“没有运动”两种假设在前后真实帧之间的亮度误差，误差更小的一方平滑胜出。向量失败时退化为线性混合，而不是撕裂。
- 小于 0.2 像素的向量视为静止内容上的估计噪声，直接按时间混合，不做重采样。
- 运动补偿取样改用 Catmull-Rom 双三次，减少重采样造成的模糊。
- 全局模型的采用门槛由 35% 降到 20%。着色器只吸附本来就与模型一致的向量，少数派模型不会带偏其余区域。
- 新增 `CHIAKI_ENHANCEMENT_FLOW_SCALE`（0.25–1，默认 1）：缩小光流分辨率以跟踪更大的位移，用于快速转向场景的对照。

这些修改尚未在 RTX 硬件上运行；着色器已通过 cs_5_0 编译。

### 2026-11-14 Flow v2 复测后的调整（候选向量选择）

v2 把慢速画面相对线性混合的劣势消除了（30–40 dB 分层由 −1.99 变为 +1.93 dB），全体平均比 DLSS FG 高 0.61 dB，但暴露出两点：逐像素比较两种假设在路杆、广告牌上产生碎点；画面边缘新进入的内容处，局部向量没有真实匹配，仍输出大片错误内容。向量精修在 v2 下不再有收益，半分辨率光流平均更差。据此：

- 自建后端每个相位改为两步。`selectMain` 在半分辨率上为中间帧的每个像素从一组候选向量里选一个：不运动（略占优）、沿向量场追踪到该像素的向量、原始向量，以及两个半径上相邻位置的向量；按前后真实帧之间 4 点小块的亮度误差取最小。遮挡边界和画面边缘处，真正覆盖该像素的相邻表面的向量会胜出。`interpolateMain` 再按选出的向量做双三次补偿取样。
- 逐像素的“运动 / 不运动”切换和 0.2 像素死区取消，改由上面的小块级选择承担，决策在空间上更稳定。
- 向量精修对两个后端都改为默认关闭（`CHIAKI_ENHANCEMENT_MOTION_REFINE=on` 开启）。

尚未在 RTX 硬件上运行；着色器已通过 cs_5_0 编译。候选选择每相位多一次半分辨率计算，耗时需要实测。

### 2026-11-14 Flow v3 与功耗验证后的调整

- 功耗验证成立：把实验台和增强进程设为“最高性能优先”后，自建后端的光流主机耗时由约 3.5 ms 降到约 1.55 ms，与 DLSS 后端一致。实时使用自建后端时建议做同样设置。
- 候选向量选择（v3）在连续更新帧上比 v2 低 0.50 dB、比 DLSS FG 低 0.78 dB，并在细杆处产生成片断裂，画面边缘的错误也未修复。纯按亮度误差选向量会选中误差碰巧较低的错误表面。因此自建后端默认恢复为 v2 的做法（`direct`），候选选择保留为 `CHIAKI_ENHANCEMENT_FLOW_SELECT=candidates`。
- 新增光流导出：`CHIAKI_ENHANCEMENT_DUMP_FLOW=<目录>` 与 `CHIAKI_ENHANCEMENT_DUMP_RANGE=<首>-<尾>`。文件为按行排列的 int16 对，单位是光流分辨率下的 1/32 像素，方向从当前帧指向上一帧。配合录像原帧即可离线复现和迭代插值算法，不必每次改动都在 RTX 机器上整套重跑。

### 2026-11-14 离线复现与前向投影插值

用导出的 NVOFA 原始网格和录像原帧，在 NumPy 中复现了自建后端：复现结果与实验台逐帧分数相差约 0.03 dB，线性混合基线一致。此后的方案先离线比较，再写入着色器。离线样本为四段素材各 8–15 个真实帧对（每对 3 个相位），全部是连续运动片段，补偿取样用双线性：

| 方案 | C01 | C02 | C03 | C04 | 平均 PSNR / dB |
| --- | --- | --- | --- | --- | --- |
| 线性混合 | 27.81 | 26.46 | 23.58 | 25.97 | 25.95 |
| DLSS FG（实验台分数） | 29.67 | 30.56 | 28.20 | 29.02 | 29.36 |
| 逐像素两假设（`direct`） | 30.13 | 30.70 | 27.83 | 28.67 | 29.33 |
| 前向投影（按着色器的计算方式） | 30.28 | 31.27 | 28.34 | 29.00 | 29.72 |
| 逐像素两假设，双三次取样 | 30.04 | 30.44 | 27.65 | 28.46 | 29.14 |
| 前向投影，双三次取样（默认配置） | 30.16 | 31.06 | 28.17 | 28.86 | 29.56 |

得到的结论：

- 向量场定义在当前帧上。原做法在中间帧位置反查向量场，新进入画面的内容（上一帧里不存在）自带无匹配的向量，会被直接放进中间帧，这是 C04 右上角亮区的原因。新做法先算每个网格向量在前后真实帧之间的匹配误差，误差超过 0.10 的向量丢弃；其余向量前向投影到时刻 t，落在同一格时匹配最好的胜出；空洞由粗到细取相邻有效向量填充，即相邻表面继续运动进入被揭开的区域。离线结果中 C04 的错误亮区基本消失。
- “运动 / 不运动”的判定逐像素做时，在 C02、C03 上各损失约 0.7 dB（细结构碎点），完全去掉又在 C01 上损失约 1.3 dB。改为在网格块上比较并做 3×3 平滑后，四段素材都不低于两者。
- 双线性取样的 PSNR 高于 Catmull-Rom，但画面更软；默认保留 Catmull-Rom，`CHIAKI_ENHANCEMENT_FLOW_SHARP=off` 可对比。
- 光流里有少量 -32768 的无效向量（约 0.1%），现在按无效处理，不再当作 1024 像素的位移。

自建后端默认改为 `CHIAKI_ENHANCEMENT_FLOW_SELECT=projected`，`direct` 和 `candidates` 保留作对照。每个相位新增约 14 次网格分辨率的计算。着色器已通过 cs_5_0 编译；C++ 接入和实际 GPU 输出尚未在 RTX 硬件上运行，离线分数是 NumPy 对同一算法的模拟，不是 GPU 实测。

## 同类功能确认

开启 VSR 时，如果已有 NR 的 FSR 重建、FSR/FSRCNNX 自定义超分或含空间超分的画质预设，会先弹出确认。确认后替换重叠处理；取消保持原设置。反向选择 FSR/FSRCNNX 或空间超分预设时同样处理。NR、色彩调整和插帧有不同用途，可以保留。

DLSS FG 与 smooth motion 在启用状态下切换也需确认。Smooth Motion 是外部驱动设置：切回 DLSS FG 时仍须在 NVIDIA App 手动关闭它，应用无法自动关闭或检测驱动的激活状态。

运行库缺失或哈希不匹配时不加载 VSR；普通缩放继续可用，同时保留可用的 NR/FG。运行库评估失败会停用 VSR 并显示原因。当前已有 HDR 限制继续生效。

## 帧率计数修复

旧浮窗只按真实帧 ID 去重：4x 的三张中间帧共用该 ID，错误地只计一次，30 fps 因而显示约 60 fps。现在使用“真实帧 ID + 生成阶段”作为标识，三张中间帧分别计数，重复渲染同一阶段不会增加帧率。

浮窗显示应用提交的真实帧、生成帧及合计。30 fps 串流的 4x 理想稳定输出约为 30 + 90 = 120 fps；首次历史预热、处理开销、实际丢帧和显示节奏会影响读数。不会直接把输入帧率乘四当作实测值，也不计入 Smooth Motion 在驱动内部生成的帧。

## 画面延迟估算

浮窗显示 `网络 + NR + 插帧 + VSR ≈ 合计 ms`，统计值约每 250 ms 更新：

| 分项 | 来源及含义 |
| --- | --- |
| 网络 | 连接阶段 Senkusha RTT 探测的一半；网络非对称会带来误差，并非实时单向测量。探测失败或未运行时显示未知，不采用连接的兜底值 |
| NR | D3D12 GPU 时间戳统计的所有 NR 遍数与重建耗时；没有 FG 时包括 NR 使用的光流 |
| 插帧 | 所有生成阶段的 GPU 时间、光流主机计时，以及生成帧排帧等待上界；因此也是保守估算 |
| VSR | VSR Evaluate 的 D3D12 GPU 时间戳差值 |

合计不包括主机编码、客户端解码、显示器扫描和外部 Smooth Motion 耗时，不能解释为完整的输入到屏幕延迟。网络未知时合计显示未知；选择 Smooth Motion 时额外显示外部耗时不可测。

## 本机验证

RTX 5070 Ti Laptop GPU 上，四档 VSR 的 640×360 → 1280×720 合成测试、NR + VSR + 4x FG 组合及 HDR NR 回归通过。组合测试为 30 张真实帧、87 张生成帧，首张用于预热。单元检查覆盖生成阶段计数、冲突检测、取消保持设置、接受替换、NR 保留及设置持久化；界面检查覆盖 VSR 选项与横向面板布局。

这些检查验证代码和 GPU 路径，不等同于真实 PlayStation 串流画质、屏幕可见帧率、端到端延迟或 GTA6 专项适配验证。
